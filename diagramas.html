Paradigma 4+1

La arquitectura de Sockbuster se documenta con el paradigma 4+1 de vistas: cuatro vistas (Lógica, Desarrollo, Procesos y Física) validadas por la vista de Escenarios. Todos los diagramas fueron elaborados en PlantUML y usan los mismos nombres de clases, componentes y nodos.

Alcance: el modelo representa la arquitectura completa que exige el caso (servicios, base de datos, HTTPS y JWT). El prototipo web implementa la interfaz (HTML, CSS y JS) con datos simulados en el navegador: catálogo con filtros (RF01), carrito y checkout (RF02), panel de administración (RF03) y reseñas con estrellas (RF04) tras un ingreso simulado con token de ejemplo (RNF02). Lo que en el diagrama es servidor, base de datos y JWT real, en el prototipo se reemplaza por JavaScript en el navegador; se despliega como sitio estático.

1. Vista Lógica

Muestra la estructura del dominio mediante un diagrama de clases. RF01 RF02 RF03 RF04

Usuario se especializa en Cliente y Administrador. Un Cliente posee un Carrito (con sus ItemCarrito), realiza Pedidos (con sus ItemPedido) y escribe Resenas sobre un Calcetin. Las Colecciones agrupan calcetines (RF01) y el Administrador gestiona stock y precios (RF03). Los atributos, métodos y multiplicidades están indicados en el diagrama.

2. Vista de Desarrollo

Organiza el software en componentes mediante un diagrama de componentes. RNF02

El Frontend Web está formado por index.html, catalogo.html, diagramas.html, estilos.css y scripts.js. Este último se comunica por HTTPS con los módulos de Catálogo (RF01), Pedidos (RF02), Inventario (RF03) y Reseñas (RF04). Los módulos de Inventario y Reseñas usan el Módulo de Autenticación JWT (RNF02). Todos los módulos acceden a la Base de Datos.

3. Vista de Procesos

Describe el comportamiento dinámico de los procesos clave mediante diagramas de secuencia.

3.1 Checkout RF02

El cliente finaliza la compra, el servidor simula la verificación de pago y abre una transacción sobre la base de datos para comprobar el stock. Si hay stock suficiente, descuenta las unidades, crea el pedido con un ID único y devuelve el resumen. Si no, revierte la transacción e informa el error. Con esto se sincroniza el acceso al stock: si dos clientes compran la última unidad al mismo tiempo, la transacción atiende a uno y revierte al otro, evitando vender más de lo disponible.

3.2 Filtrado del catálogo RF01

Al elegir una colección, el frontend solicita al servidor los calcetines de esa colección, que consulta la base de datos y devuelve foto, precio, stock y tallas para mostrarlos al cliente.

4. Vista Física

Muestra la topología de despliegue mediante un diagrama de despliegue. RNF01 RNF02

El navegador del usuario accede por HTTPS al contenido estático servido desde una CDN (carga inicial en menos de 2 segundos, RNF01). El sitio se publica como contenido estático en un hosting web gratuito (por ejemplo GitHub Pages). En el modelo completo, el hosting en la nube aloja el Servidor Web (frontend y servicios del sistema) y el Servidor de Base de Datos. Las funciones administrativas viajan por HTTPS con token JWT (RNF02).

Historias de usuario

  • HU1 (RF01): Como cliente quiero filtrar por colección para encontrar rápido calcetines de mi película favorita. Valida: Coleccion, Módulo Catálogo, secuencia de filtrado, CDN.
  • HU2 (RF02): Como cliente quiero finalizar mi compra y recibir un ID de pedido para confirmar mi orden. Valida: Pedido, Módulo Pedidos, secuencia de checkout, Servidor de BD.
  • HU3 (RF03, RNF02): Como administrador quiero actualizar stock y precios con sesión autenticada para mantener el inventario al día. Valida: Administrador, Módulo Inventario + JWT, HTTPS.
  • HU4 (RF04): Como cliente registrado quiero publicar una reseña de 1 a 5 estrellas para compartir mi opinión. Valida: Resena, Módulo Reseñas, Vista Física.
